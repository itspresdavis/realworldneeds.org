# English and Spanish interface

The interface uses the same public URLs and catalog IDs in both languages. English remains the server-rendered, indexed source. There are no separate Spanish service pages or Spanish `hreflang` claims. The language control changes document language and reviewed interface text in place, preserving entered search/form values, selection, links, history and Saved IDs. The only preference stored is `rwn-language` (`en` or `es`); it is not sent to analytics. Storage denial leaves the in-memory control usable. Clear browser data removes this preference as well.

`src/utils/localization.js` owns reusable message keys and date-only formatting. `src/utils/interface-copy.js` contains reviewed RWN interface copy and bounded numeric/status patterns for existing renderers. `public/language.js` applies those messages without replacing controls or using HTML interpretation. It observes new interface nodes, disconnects while making its own changes, and leaves provider facts alone. `originalText(element)` preserves the English status contract used by the legacy offline recovery renderer; new state logic should use explicit state instead of comparing display text.

Provider names, addresses, eligibility, entrances, schedules, service descriptions and contact values are not machine-translated. Source-backed facts retain their original content and language metadata. The Spanish control explains that some text retains its original language and that translating RWN does not establish a provider's ability to serve someone in Spanish. Long-form English policy content is explicitly marked `lang="en"`. Authored, reviewed bilingual content can use `data-i18n-en` and `data-i18n-es` on text-only elements; `data-i18n` selects a centralized key. Neither mechanism can insert HTML. `data-provider-text` excludes source text from interface interpretation.

Do not translate input values, option values, identifiers, URL destinations or private report text. Newly authored interface code should use message keys at rendering boundaries; the allowlisted adapter exists to preserve the existing rendering architecture while it is incrementally localized. An unrecognized message falls back to its original text. Add a reviewed pair and a behavior test when a new core journey introduces a message. Contributor/reviewer messages belong to their protected UI's own approved dictionary, using the shared language-change event.

## Build, offline and performance

Run `scripts/build-localization.mjs` after every HTML generator and before asset/worker fingerprinting. It produces a self-contained public language module and injects the shared task-control CSS. Include `/language.js` and `/task-controls.css` in the existing content-hashed offline assets and worker inputs. An older cached entry without this optional layer remains a usable English finder; no Saved schema migration is required.

Existing script/style/search budgets remain unchanged. The new feature has initial ceilings of 30,000 raw / 10,000 gzip bytes for its module and 3,000 raw bytes for shared access/search/language control CSS. These bounds cover both languages' controls, access and Saved messages, unavailable/offline recovery copy, and the compatibility adapter. The measured module is about 29 KB raw / 9.8 KB gzip and CSS 2.3 KB. No framework, font or runtime dependency was added. Copy growth should trigger consolidation or a separately versioned deferred language resource rather than silently raising these ceilings.

Bounded local diagnostics at Chromium 158, 390×844, CPU throttled 4× measured six native language changes per route, ending at the second animation frame. Directory changes were variable (123–308 ms after observer optimization); these are lab interaction timings, not field INP or a performance-target pass. The whole candidate still needs the shared comparable baseline/candidate performance run. Detailed logs and screenshots remain in external QA evidence, not source.

## Verified journeys and limits

Focused Chromium and Firefox tests cover mobile eligibility at 320/390/768/1440, 200% text, language task preservation, Saved IDs, original destinations, blocked storage, translated detail accessibility, and a settled translation observer. Additional tests cover locale parameters, date-only calendar stability, unknown text fallback, safe text handling, preference clearing, generated-module identity and budgets. Final integration must rerun these on the candidate with its real build and offline pipeline, including WebKit and old-worker recovery. Browser emulation is not a physical mobile device or screen-reader acceptance result. No provider translation or language capability is certified by these tests.
